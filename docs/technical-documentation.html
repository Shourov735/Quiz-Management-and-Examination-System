2. Domain Modeling & System Requirements

2.1 Domain Analysis & Core Challenges

The examination domain presents specific architectural challenges that cannot be solved cleanly with procedural code:

  1. Polymorphic Question Structures: Examinations combine single-answer MCQs, binary True/False, open-ended Fill-in-the-Blank, and multi-selection Multiple-Answer questions. Each type has different option schemas and validation rules.
  2. Pluggable Scoring Policies: Standard grading uses flat scoring; competitive exams penalize guessing via negative marking; rapid-fire tests award speed bonuses. Hardcoding these in the service layer violates the Open/Closed Principle.
  3. Guarded Operational Lifecycles: A quiz moves from DRAFT to PUBLISHED, ACTIVE, COMPLETED, and ARCHIVED. Actions such as editing questions or initiating student attempts depend strictly on the active state.
  4. Session Event Decoupling: During live examinations, events such as answer submission and timer expiration must trigger UI updates, autosave, and score computation without coupling the examination runner to GUI widgets.

2.3 Core Business Invariants

  • Publication Invariant: A quiz cannot transition from DRAFT to PUBLISHED unless it has a non-empty title and at least one question with positive marks.
  • Attempt Eligibility Invariant: Students can only take exams in PUBLISHED or ACTIVE status, provided completed attempts < max_attempts (where 0 indicates unlimited attempts).
  • Immutability Invariant: When an attempt reaches SUBMITTED or TIMED_OUT, its recorded answers, duration, and score are permanently sealed.

3. Layered System Architecture

The application employs an enterprise 5-tier architecture that guarantees strict separation of concerns, high maintainability, and testability.

Figure 3.1: Layered Architecture of the Quiz Management & Examination System.

3.1 Detailed Layer Responsibilities

  • Presentation Layer: JavaFX FXML files declare layout hierarchies; controller classes implement Initializable, receive user input, invoke business services, and update JavaFX observable properties. Controllers contain zero business logic and zero SQL statements.
  • Service Layer: Coordinates transactions and business invariants. Classes (QuizService, AttemptService, etc.) receive repositories via constructor injection, enabling seamless mocking during unit tests.
  • Domain & Patterns Layer: Rich domain models (Quiz, Question, QuizAttempt) encapsulate their own validation and internal state. Design patterns (Strategy, State, Factory Method, Observer) operate directly in this layer.
  • Repository Layer: Decouples domain logic from SQL. Repository interfaces define CRUD and query contracts; SQLite implementations use PreparedStatement and try-with-resources to prevent SQL injection and connection leaks.
  • Database Layer: SQLite embedded relational engine ensuring ACID transactions, foreign key enforcement (PRAGMA foreign_keys = ON), and automated schema setup.

4. In-Depth Design Patterns Evaluation

The project implements four Gang-of-Four (GoF) design patterns plus the Singleton and Repository patterns. Each pattern addresses a specific architectural problem and provides measurable extensibility benefits.

4.1 Strategy Pattern — Scoring Algorithms GoF Behavioral

Problem Addressed

Examinations require diverse grading formulas: standard flat marking, negative marking penalties, and time-based bonuses. Embedding these variations in a monolithic evaluation loop using nested if/else statements violates the Open/Closed Principle (OCP) and tightly couples scoring logic to attempt orchestration.

Solution & Participants

  • ScoringStrategy: Strategy interface declaring double calculateScore(List<Answer> answers, double totalMarks, int timeLimitSeconds, int timeSpentSeconds).
  • StandardScoring: Sums marksAwarded for all correct answers.
  • NegativeMarkingScoring: Deducts a penalty fraction (default 0.25) of the average question mark for each incorrect response, bounded at 0.
  • TimeBasedScoring: Awards a 10% bonus for finishing in <50% of the time limit and a 5% bonus for <75%, capped at total marks.
  • ScoringStrategyFactory: Dynamically instantiates the requested strategy by name.
Figure 4.1: Strategy Pattern class structure for modular examination scoring algorithms.

Alternatives Considered & Trade-offs

  • Inline Switch in Service: Simpler initially, but violates OCP and requires modifying service code whenever grading policies change. Rejected.
  • Subclassing Quiz (e.g. NegativeMarkingQuiz): Couples quiz behavior to quiz metadata and produces class explosion when combined with timed/shuffled variations. Rejected.

Future Benefit: Introducing algorithms like PartialCreditScoring or DifficultyWeightedScoring requires only implementing ScoringStrategy without touching AttemptService.

4.2 State Pattern — Quiz Lifecycle Governance GoF Behavioral

Problem Addressed

A quiz progresses through multiple distinct operational phases: DRAFT → PUBLISHED → ACTIVE → COMPLETED → ARCHIVED. Allowed actions depend strictly on the active state. Scattering status checks (if (quiz.getStatus() == QuizStatus.DRAFT)) across controllers leads to code duplication and invalid state bugs.

Solution & Participants

  • QuizState: Interface declaring transition operations (publish, unpublish, activate, complete, archive) and capability queries (canBeAttempted(), canBeEdited(), canAddQuestions()).
  • DraftState: Permits question editing; transitions to PUBLISHED or ARCHIVED.
  • PublishedState: Enables student attempts; locks question editing; transitions to DRAFT, ACTIVE, or ARCHIVED.
  • ActiveState: Represents in-session exams; transitions to COMPLETED.
  • CompletedState: Closed examination; transitions to ARCHIVED.
  • ArchivedState: Terminal state; forbids all state mutations and throws IllegalStateException on invalid actions.
  • QuizStateManager: Context maintaining the current state and synchronizing Quiz#status.
Figure 4.2: Finite State Machine governing Quiz lifecycle transitions.

4.3 Factory Method Pattern — Question Polymorphism GoF Creational

Problem Addressed

The question bank supports MCQ, True/False, Fill in the Blank, and Multiple Answer questions. Each requires distinct options parsing and answer validation algorithms. Direct instantiation in repository and controller code produces tight coupling to concrete types.

Solution & Participants

  • Question (Abstract Product): Defines core fields and abstract methods validateAnswer(String answer) and getCorrectAnswerDisplay().
  • Concrete Products: MCQQuestion, TrueFalseQuestion, FillBlankQuestion, MultipleAnswerQuestion.
  • QuestionFactory (Creator): Provides createQuestion(QuestionType type) and createFromResultSet(ResultSet rs) to deserialize SQLite rows into polymorphic subclasses based on the question_type column.
Figure 4.3: Factory Method Pattern generating polymorphic question products.

4.4 Observer Pattern — Quiz Session Events GoF Behavioral

Problem Addressed

During examination attempts, session events (answer submitted, timer expired, attempt completed) must notify multiple independent components (progress bar, timer listener, score cache) without coupling the examination runner to GUI controls.

Solution & Participants

  • QuizEventPublisher: Thread-safe subject with subscribe, unsubscribe, and publish guarded by a ReentrantReadWriteLock.
  • QuizEvent: Event enum (ATTEMPT_STARTED, ANSWER_SUBMITTED, SCORE_UPDATED, QUIZ_COMPLETED, TIME_EXPIRED).
  • QuizEventListener: Observer interface with onEvent(QuizEvent event, Object data).
  • Concrete Observers: ProgressTracker (computes percentage and running score) and TimerListener (monitors expiration).

4.5 Singleton Pattern — SQLite Connection Manager GoF Creational

Academic Justification: SQLite is an embedded file-based database. Creating multiple uncoordinated connections from concurrent threads results in SQLITE_BUSY lock contention. DatabaseConnection uses thread-safe double-checked locking to serialize write operations, enable PRAGMA foreign_keys = ON, and run schema migrations. Singleton is strictly restricted to this physical resource manager and avoided across all services.

4.6 Repository Pattern — Data Access Decoupling Architectural

Six repository interfaces (UserRepository, QuizRepository, QuestionRepository, QuizAttemptRepository, AnswerRepository, CategoryRepository) abstract SQLite JDBC operations using PreparedStatement and try-with-resources. Services depend on repository abstractions via constructor injection, enabling testing with Mockito.

10. Viva Defense & Demonstration Guide

This section prepares both team members for the oral examination and project demonstration:

Q1: Why did you use Strategy for scoring instead of polymorphism on Quiz?

Answer: A quiz varies across multiple independent dimensions: scoring strategy (Standard, Negative, Time-based), time constraints (timed vs untimed), and question ordering (shuffled vs fixed). Subclassing Quiz to vary scoring creates class explosion (e.g., NegativeMarkingTimedShuffledQuiz). Strategy encapsulates the scoring algorithm into an interchangeable object, enabling new grading algorithms to be added without touching the quiz entity.

Q2: How does the State Pattern prevent bugs compared to a status enum?

Answer: With a status enum and switch statements, validation logic is scattered across every service method, making it easy to forget checking status before mutating data. In our State Pattern, each state class encapsulates allowed operations and throws an IllegalStateException if an invalid action is attempted (e.g., DraftState.canBeAttempted() == false; ArchivedState.publish() throws). Invalid operations fail immediately at the domain layer.

Q3: How is the Factory Method Pattern utilized when loading questions from SQLite?

Answer: When querying the questions table, the application reads the question_type column. QuestionFactory.createFromResultSet(rs) inspects this value and instantiates the correct subclass (MCQQuestion, TrueFalseQuestion, etc.). The repository operates purely on the Question abstraction without needing to know subclass constructors.

Q4: Why is your use of the Singleton Pattern justified in an academic project?

Answer: In our project, Singleton is used strictly for the DatabaseConnection manager to coordinate access to the single embedded SQLite file and prevent SQLITE_BUSY lock errors. We consciously avoided Singletons for business services, repositories, and controllers, opting for constructor dependency injection to ensure testability with Mockito.

Q5: How did you ensure testability of services without depending on SQLite?

Answer: We applied the Repository Pattern and Dependency Inversion Principle (DIP). Services accept repository interfaces rather than concrete SQLite classes. In our JUnit 5 tests (e.g., QuizServiceTest), we inject Mockito mocks (@Mock QuizRepository), allowing service business rules to be tested in isolation in milliseconds without database I/O.
